The build brief

This is the brief the app was built from, as it was given to Claude Code.

Customer Signal

What I want to build

I want to build a polished web app that takes a CSV of customer reviews and turns it into a useful picture of what customers want fixed.

The basic idea is:

Upload messy customer feedback → identify recurring pain points → turn those pain points into product priorities.

This is for a live vibe-coding demonstration with first-year MBA students. I want it to feel like a real product that a product manager could hand to someone else, not a dashboard built around one particular dataset.

The app should be called Customer Signal, with the tagline:

Turn customer feedback into product priorities.

Create an original, modern logo for Customer Signal in Sloan red (#a31f34). It should feel like the identity of a real contemporary analytics product, work both prominently on the opening screen and at a smaller size in the app header, and avoid generic robot, brain, or AI-sparkle imagery.

Uploading data

The app should accept any CSV file and then ask the user to identify which columns contain:

  • Review text — required
  • Rating — optional
  • Date — optional
  • Review title — optional
  • Any other columns that might be useful for comparison, such as customer segment, product, geography, or device

It should make reasonable guesses based on the column names, while letting the user change them. Show a preview of the data before analysis begins.

The app should not assume a particular company, product, or CSV structure. Review text should be the only required field. If useful optional columns are missing, the corresponding analyses should simply be omitted.

The opening screen should be visually strong and simple: a large drag-and-drop area, a file picker, and a short explanation of what the app does. After the columns are mapped, the user clicks Analyze reviews.

The analysis should work in a reasonable amount of time for several thousand reviews. Show progress while it runs so the app does not appear frozen.

Results

Once the analysis is complete, show a compact summary with the number of reviews analyzed, average rating if available, number of pain points found, and date range if available.

Below that, use four tabs:

  1. Priorities
  2. Roadmap
  3. Additional Insights
  4. Details

If the data contains useful comparison columns, add filters for them. Filtering the data should update the analysis and charts, not just the labels on the page.

1. Priorities

This should be the visual centerpiece of the app.

Create a chart that places each pain point according to:

  • X-axis: how frequently it appears
  • Y-axis: how severe the customer experience is
  • Color: a broader category that the app derives from the pain points

Use roughly 3–5 broader categories, but let the number vary when the data calls for it. The individual pain points should be specific enough to imply different responses. “App repeatedly disconnects” is useful; “product quality” is not.

Keep the circles approximately the same size. Frequency is already represented by horizontal position, so circle size should not repeat the same information.

Divide the chart into four lightly marked areas:

Lower frequency Higher frequency
Higher severityWatch closelyFix first
Lower severityLower priorityImprove at scale

When the user hovers over a pain point, show only its name and one representative quotation.

When the user clicks it, open a window or side panel with:

  • Frequency and number of matching reviews
  • Severity
  • Average rating, if available
  • A short explanation of what customers are experiencing
  • A proposed response
  • Several representative quotations
  • A way to inspect the underlying matching reviews

Every quotation must come directly from the uploaded data. Do not invent or rewrite customer language.

2. Roadmap

Turn the findings into a visually impressive Now → Next → Later product roadmap.

This should look like a real roadmap board, not a Markdown list or an ordinary table. Each recommendation should be a card with:

  • A concrete, action-oriented recommendation
  • A short explanation
  • The pain point or pain points it addresses
  • A tag for the function that would probably own it

Possible functional tags include:

  • Engineering
  • Product / UX
  • Customer Experience
  • Operations
  • Pricing / Commercial
  • Marketing / Education

The app can combine multiple pain points into one recommendation when they plausibly call for the same response.

Do not estimate implementation effort or add a generic “customer impact” score. The reviews do not contain enough information for that. The Now/Next/Later placement is the recommendation.

Clicking a roadmap card should reveal the reasoning and customer evidence behind it.

3. Additional Insights

Use whatever other columns are available to suggest 2–5 additional graphs that could help someone understand the feedback.

For example:

  • Are particular problems concentrated in one product or customer segment?
  • Are complaints becoming more or less common over time?
  • Do users on one device report an issue more often than users on another?
  • Which pain points are most strongly associated with low ratings?

The useful graphs will depend on the data. Do not produce a chart for every column merely because the column exists. Choose a small number of analyses that reveal the strongest or most decision-relevant patterns.

Each graph should have a specific title that states the finding, followed by a short interpretation. For example:

Android users mention connection failures 2.4× as often as iOS users.

If the CSV contains no useful additional columns, show a thoughtful empty state rather than inventing an insight.

4. Details

This tab should make the analysis transparent and inspectable.

Explain precisely:

  • How recurring pain points were identified
  • How reviews were assigned to one or more pain points
  • How frequency was calculated
  • How severity was judged
  • How the broader categories were created
  • How representative quotations were selected
  • How roadmap recommendations were produced and ordered
  • How the additional graphs were selected

Frequency should mean the percentage of reviews that mention a pain point. A review should count only once toward a pain point even if it mentions the issue repeatedly.

Severity should reflect the consequence described by the customer, not simply reverse the star rating. A review saying “I wish it came in blue” should not be treated like one saying “the battery overheated and damaged my desk.”

If the analysis uses model judgments, say what the model judged. If it uses topic modeling, keywords, sentiment, ratings, or rules, identify those methods and explain how they affect the result. Do not use vague language such as “AI-powered analysis” in place of an actual explanation.

Also show the current analysis settings: the uploaded filename, number of reviews, columns used, methods used, and when the analysis was run.

Visual direction

I want every page and state of the app to look impressive, modern, and intentionally designed—not just the final dashboard. The upload screen, column-mapping flow, analysis progress, each results tab, detail panels, and empty states should all have a strong visual focal point rather than feeling like forms or text placed inside boxes.

Use dynamic visual elements throughout: responsive hover states, smooth chart transitions, animated analysis progress, subtle movement when filters change, and polished transitions between views. The movement should help communicate what the app is doing rather than feeling decorative or distracting.

Overall, this should look like a modern product-analytics tool rather than a generic admin dashboard.

Use a restrained Sloan-inspired visual style:

  • Sloan red (#a31f34) as the main accent
  • Charcoal text, white cards, and a light warm-gray background
  • A distinct, readable color for each pain-point category
  • Strong hierarchy, generous whitespace, thin rules, and compact charts
  • Subtle motion for hovering, changing tabs, opening panels, and filtering
  • The original Customer Signal logo used consistently across the opening screen and app header

Avoid decorative gradients, glass effects, generic AI sparkles, oversized metric cards, and a left-hand admin sidebar. Do not use the MIT logo or present this as an official MIT product.

The roadmap should feel especially polished. The priority chart should remain legible even when there are a dozen or more pain points.

A few important rules

  • Do not hard-code the results for one dataset.
  • Do not fabricate quotations, counts, trends, or precision.
  • Do not force every review into a pain point; positive reviews may contain none.
  • A review may mention more than one pain point.
  • Let the number and names of pain points respond to the data.
  • Handle missing optional columns gracefully.
  • Make every visible button and interaction work.
  • Keep the methodology consistent with what the app actually does.
  • Use whatever technical approach you think is most appropriate. I care about the behavior and finished experience, not a particular framework.

What counts as finished

The app is finished when I can:

  1. Upload an unfamiliar CSV.
  2. Map its columns and preview the data.
  3. Analyze several thousand reviews without the interface freezing.
  4. Explore the severity × frequency chart by hovering, clicking, and filtering.
  5. Inspect the customer evidence behind any pain point.
  6. View a polished Now/Next/Later roadmap.
  7. See a small set of useful analyses based on the other available columns.
  8. Understand exactly how the app produced its results.

Please run the app, test the complete upload-to-results flow, and fix visible or functional problems before you finish. Include a short README explaining how to start it.

If a missing decision would materially change the product, ask me. Otherwise, make reasonable choices and proceed.
